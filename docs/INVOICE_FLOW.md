# Per-Invoice Flow — `customers.txt` model

The single-file customer registry. The only file you touch.

## How to issue / revoke a customer

`nexora-releases/customers.txt`:

```
alice@example.com:inv_2026_001
bob@example.com:inv_2026_002   # vip, lifetime
# carol@example.com:inv_2026_003   ← revoked
```

Rules:
- Append a line `email:invoice_id` → customer issued.
- Prefix the line with `#` → customer revoked.
- Save + push → `auto-build` workflow fires.
- Allowed invoice id charset: `[A-Za-z0-9._-]{4,64}`.

Don't manually edit `invoices/*.json`. They are artifacts regenerated by
the workflow from `customers.txt`.

## What happens on each push

```
customers.txt change
         │
         ▼
.github/workflows/auto-build.yml  (on nexora-releases)
  ├─ parse customers.txt
  ├─ for each new "active" line:
  │     sign payload with NEXORA_SIGNING_KEY → invoices/<id>.json
  ├─ for each commented-out line that was previously active:
  │     re-sign with status=revoked
  ├─ delete stray invoice JSONs not referenced anymore
  ├─ commit invoices/ back
  ├─ pull latest version from versions/stable.json
  └─ for each newly-active invoice:
         dispatch customer-build.yml on 8w6s/nexora-paid
         (build args: NEXORA_INVOICE_ID, NEXORA_INVOICE_EMAIL, version)
                  │
                  ▼
       ghcr.io/8w6s/nexora-backend:<version>-<invoice_id>
```

End-to-end takes ~2 minutes from `git push` to image-on-GHCR.

## Status states

| invoice file says | banner | paid plugins |
|---|---|---|
| `status: active`    | green  | ✅ load |
| `status: revoked`   | red    | ❌ off  |
| `status: suspended` | amber  | ❌ off  |
| (missing / 404)     | red    | ❌ off  |

`suspended` is set manually (edit `invoices/<id>.json` by hand and re-sign
with `scripts/sign-invoice.ts`). The `customers.txt` flow only produces
`active` or `revoked`.

## Manual one-off invoice (rare)

If you need to issue something `customers.txt` can't express (custom
`expiresAt`, `features` allowlist for tier gating, hand-written note):

```bash
bun run scripts/sign-invoice.ts \
  --id=inv_2026_042 \
  --email=customer@example.com \
  --features=search-suggest,admin-bulk \
  --expires=2027-12-31T23:59:59Z \
  --note="annual + feature-limited"
```

Commit `issued/inv_2026_042.json` into `nexora-releases/invoices/`
manually. Skip the customers.txt entry — the workflow ignores invoice
files that have no corresponding line UNLESS that file's id ever
appeared in customers.txt before (in which case the workflow will
overwrite it on the next push, so don't mix the two models).

## Verifying the loop

Always works locally — sign a test invoice and verify the signature with
the same pubkey the backend embeds:

```bash
bun run scripts/sign-invoice.ts --id=inv_smoke --email=demo@example.com \
  --out=./issued/inv_smoke.json
# Then open issued/inv_smoke.json; signature should be a 128-char hex
# string that verifies under b20fc903…44e3.
```

## Required secrets / variables

On `8w6s/nexora-paid`:
- secret `NEXORA_SIGNING_KEY` — hex bytes of `.keys/license-signer.private`
- secret `RELEASES_REPO_TOKEN` — fine-grained PAT with `contents: write` on `nexora-releases`
- variable `NEXORA_RELEASES_REPO = 8w6s/nexora-releases`

On `8w6s/nexora-releases`:
- secret `NEXORA_SIGNING_KEY` — same hex bytes as above
- secret `PAID_DISPATCH_TOKEN` — PAT with `actions: write` on `nexora-paid`

All set. Don't rotate any of them without re-running each release
workflow against the new key.
